# 14. 古典的な画像認識 (`doc/14-classic-vision.md`)

`UnityBackend/ArsistBuilder/Assets/Arsist/Runtime/Perception/Vision/Classic/`

## 1. なぜ古典的な手法なのか

画像アンカー (`doc/11-perception.md`) は「登録した写真を探す」ためのもので、ORB で特徴を取る。
これは強力だが、**登録していないものについては何も分からない**。

一方で AR の現場でやりたいことの多くは、「今見えているものがどうなっているか」を測るだけで足りる。

- この部品は何色か
- 赤いランプはいくつ点いているか
- 枠の中にあるのは丸か四角か
- 空は曇っているか

これらに学習モデルは要らない。古典的な手法で十分な精度が出るうえ、次の点で明確に有利。

| | 古典的な手法 | 学習モデル |
|---|---|---|
| モデルの配布 | 不要 | APK に同梱するか、初回に落とす |
| 対応端末 | どこでも動く | NNAPI / GPU 依存 |
| 実行時間 | 480px で数〜数十 ms | 端末次第 |
| 挙動の説明 | 手順として説明できる | 説明しにくい |
| 数値検証 | `npm run test:perception` で完結 | 実機とデータセットが要る |

最後の一点が実際には一番効く。Unity ビルドを通さずに `dotnet` だけで検証できるので、
符号やしきい値の間違いをその場で潰せる。

## 2. 構成

**すべて UnityEngine に依存しない。** Unity に触るのは `ColorImageUnity.cs` だけ。
これは `tools/perception-check` が素の .NET でそのままコンパイルするための制約で、
崩すと数値検証ができなくなる。

| ファイル | 中身 |
|---|---|
| `ColorImage.cs` | RGB24 の画（行は下から上、`GrayImage` と同じ規約）。HSV 変換は整数のみ |
| `MaskImage.cs` | 0/255 のマスク。固定しきい値・大津法・HSV 範囲・モルフォロジー（2 パスの分離実装） |
| `ConnectedComponents.cs` | 4 連結のラベリング。面積・外接矩形・重心・充填率 |
| `EdgeDetector.cs` | Sobel と Canny |
| `Contours.cs` | Moore 近傍による輪郭追跡、Douglas-Peucker、形の分類 |
| `TemplateMatcher.cs` | 正規化相互相関 (NCC) によるテンプレートマッチング |
| `SkySegmenter.cs` | 空の抽出と青空への塗り替え |
| `ClassicAnalyzer.cs` | 上記をタスクとして呼ぶ窓口。DataStore 用の辞書で返す |
| `ColorImageUnity.cs` | Color32 / Texture2D との橋渡し（唯一 UnityEngine に触る） |

## 3. 使い方

Perception タスクの種類を `analyze` にして、`analysis.kind` を選ぶ。

| kind | 返るもの | bind の例 |
|---|---|---|
| `color` | 代表色 | `<storeAs>.name` `.hex` `.hue` |
| `blobs` | 指定した色の塊 | `.count` `.coverage` `.items[0].x` |
| `shapes` | 輪郭の形 | `.count` `.square` `.items[0].shape` |
| `sky` | 空の状態 | `.condition` `.coverage` `.brightness` `.saturation` |

OCR タスクと同じく、結果は **DataStore に辞書ひとつ**で入る。
`ArsistDataStore.TryGetValueByPath` がドットパスを辿るので、
`<storeAs>.status` と `<storeAs>.condition` を同じ書き方で bind できる。
件数が可変な `items` は添字でも辿れる（`items[0].x` でも `items.0.x` でもよい）。

`sky` のときだけ `previewBindingId` を指定でき、塗り替えた画が
その bindingId を持つ Image / RawImage 要素に描かれる。

デモは `products/BlueSky`（曇り空を青空にする）。

### 色つきフレームの扱い

追跡は輝度だけで足りるので、カメラソースは通常 `GrayImage` しか作らない。
`analyze` タスクだけが色を要るので、`IArsistCameraFrameSource.CaptureColor` を
**その静止画を撮るフレームでだけ**立てる。毎フレーム RGB に変換すると、
使いもしない変換で端末が温まる。

## 4. 実装上、間違えやすかったところ

数値検証で実際に捕まえたものを残す。同じ罠は繰り返し踏むので。

- **大津法の返り値の意味**。大津法が選ぶ `t` は「背景 = `t` 以下」を意味する。
  `Threshold.Fixed` は `value >= threshold` なので、そのまま渡すと背景まで前景に入り、
  **画像全体が真っ白なマスクになる**。前景の下限 (`t + 1`) に直して返している。
- **閉じた輪郭に対する Douglas-Peucker**。素の DP は始点と終点を必ず残すので、
  追跡を始めた場所が辺の途中だと偽の頂点が 1 つ残り、**正方形が五角形になる**。
  始点から最も遠い点をもう一方の錨にして、二つの弧に分けてから掛ける。
- **連結成分ラベリングの再帰**。空のように広い領域では、再帰版はスタックを溢れさせる。
  明示的なスタックを使う。400x400 全面のケースをテストに入れてある。
- **画像の最上行の勾配は必ず 0**。Sobel の窓が画像外に出るため。ここから空の走査を
  始めると、地面しか写っていない画像でも上端が空に化ける。1 行下から始める。
- **色相のヒストグラムの山の中心**。窓の中心をそのまま代表色にすると、真っ赤のように
  色相が一点に固まった画で最大 15 度ずれ、**赤がオレンジと呼ばれる**。窓の中で重み付き平均を取る。
- **面積だけで空を判定しない**。明るくて上のほうにある模様のある物体（木の茂み、白い壁）は
  面積の条件を満たしてしまう。抽出後に**平均勾配**を見て弾く。合成データでは
  空 1.34 に対して地面 10.35 と、はっきり分かれる。
- **明るさ・平坦さ・曇り判定を絶対値で切らない**。どれも「暗い場面ではまるごと落ちる」
  という同じ壊れ方をする。§5 参照。

## 5. 空の抽出の手順

学習を使わず、空の持つ性質を順に使う。

1. **上側にある** — 列ごとに上から降りて、最初にぶつかった強いエッジを空の下端とする
2. **境界をならす** — 中央値で平滑化する。電線や枝で 1 列だけ跳ね上がるのを抑えるため
3. **明るさのしきい値を画像から決める** — 下記
4. **彩度で絞る** — 曇天も晴天も彩度は高くない
5. **穴と欠けを整える** — 閉じてから開く
6. **平坦さで最終確認** — 空は平坦。ここが甘いと誤検出が増える

### 薄暗い空を落とさないために

**明るさは絶対値で切らない。** 固定の下限 (90) だと、夕方や曇りの濃い日の
「暗いが確かに空」がまるごと落ちる。空かどうかを決めるのは絶対的な明るさではなく、
**地面より明るく、平坦で、上にある**こと。

そこで、境界より上の領域そのものの輝度の**中央値の半分**をしきい値にする。
空は境界より上のほとんどを占めるので中央値はほぼ空の明るさで、その半分なら、
雲の暗い側や地平線際の減光は残しつつ、紛れ込んだ暗い物体は落ちる。
昼の空では `MinBrightness` (90) で頭打ちにして従来の挙動をそのまま保ち、
下は `MinBrightnessFloor` (20) で止める。合成データでの実測:

| 空の明るさ | 使われたしきい値 | 取れた割合 (正解 0.40) |
|---|---|---|
| 195 (昼) | 90 | 0.383 |
| 110 | 54 | 0.389 |
| 70 (夕方) | 34 | 0.391 |
| 30 (ほぼ夜) | 20 | 0.378 |

**平坦さも絶対値だけでは切らない。** 暗い場面ではセンサーノイズが乗って空でも勾配が上がる。
そこで、地面側の平均勾配と比べて `RelativeFlatness` (0.6) より平坦なら、絶対値の門
(`MaxSkyGradient` 8) を越えていても空と認める。合成データでの実測は、ノイズの乗った
薄暗い空が 0.45、地面しか写っていない誤検出が 0.94 で、その間に置いてある。

### 曇りか晴れかは彩度で分ける

`condition` を明るさで決めると、**夕方の青空がまとめて曇り扱い**になる。
曇り空は灰色なので彩度がほぼ無く、晴れた空は暗くても青いまま彩度が残る。
実測では、薄暗い青空 130 に対して薄暗い曇り空 21。しきい値は 60。

塗り替え (`SkySegmenter.Repaint`) は、一様な青で塗り潰さずに**元の輝度の揺らぎを残す**。
曇り空の雲がそのまま青空の雲になる。上ほど濃く、地平線に近いほど淡くするのも、
本物の空の見え方に合わせるため。強さは `repaintStrength` で 0〜1。

## 6. 検証

```bash
npm run test:perception
```

`tools/perception-check/ClassicChecks.cs` が合成画像で全演算子を確認する。
色空間・しきい値・モルフォロジー・ラベリング・エッジ・輪郭・テンプレートマッチング・
空の抽出と塗り替え、`ClassicAnalyzer` の入出力、そして `ArsistDataStore` のパス解決まで。

**しきい値や符号を触ったら必ず通すこと。** これらは間違っていてもコンパイルは通り、
実機では「なんとなく違う」としか分からない。
